
## Кейс: образовательная платформа «Курсатор»

---

## Этап 1. Постановка задачи

Платформа «Курсатор» — онлайн-обучение: пользователи проходят курсы, сдают тесты, общаются на форуме. Есть авторы курсов, модераторы, аналитика.

**Задача:** распределить 9 сущностей/потоков между хранилищами (PostgreSQL, Redis, MongoDB, ClickHouse — либо другие, если есть обоснование), учитывая операции, характер нагрузки и требования к целостности/скорости.

**Доступные хранилища и их роль (по материалу лекции):**
- **PostgreSQL** — реляционная СУБД, OLTP, ACID, JOIN и внешние ключи. Подходит там, где важна целостность данных и связи между сущностями (транзакции, финансы, учёт).
- **Redis** — key-value, доступ по ключу + TTL. Подходит для кэша, сессий, счётчиков — там, где важна скорость, а не сложные запросы.
- **MongoDB** — документная БД, гибкая схема (JSON), удобна для полуструктурированных данных с разным набором полей.
- **ClickHouse** — OLAP, колоночное хранение, оптимизирован под тяжёлые агрегаты по огромным объёмам исторических данных, а не под частые мелкие записи.
- *(при необходимости)* **Elasticsearch** — полнотекстовый поиск с ранжированием; **Neo4j** — граф связей для рекомендаций.

**Что нужно на выходе:** заполненная таблица анализа (Этап 2), Data Placement Map (Этап 3), схема синхронизации (Этап 4), список спорных решений и Git Issue.

**Ответы на вопросы для обсуждения:**
- **Источник истины** — там, где данные создаются впервые: Пользователи, Курсы, Прогресс, Форум → PostgreSQL.
- **Что кэшируется** — сессии (TTL минуты/часы), профиль пользователя (TTL ~15 мин), рейтинг рекомендаций.
- **Для аналитики** — данные производные (копия логов и прогресса, агрегированные в ClickHouse), а не сырые.
- **ACID нужен** — пользователи, курсы, прогресс (деньги/оценки не теряем). **Eventual consistency допустима** — поиск, рекомендации, аналитика, кэш.

## Этап 4. Синхронизация и потоки данных

```
Пользователи        → PostgreSQL → CDC/событие "user.updated"      → Redis (кэш профиля, TTL 15 мин)
Курсы и уроки        → PostgreSQL/MongoDB → событие "course.published" → Elasticsearch (поисковый индекс)
Прогресс по курсам   → PostgreSQL → батч-задача (раз в час)         → ClickHouse (для аналитики)
Логи действий         → ClickHouse (пишутся напрямую потоком)       → -
Логи + Прогресс       → ClickHouse → SQL-агрегаты                   → Аналитика/отчёты (витрины в ClickHouse)
Пользователи + Курсы  → PostgreSQL → батч-задача (раз в сутки)      → Neo4j (граф для рекомендаций)
```

**Механизм синхронизации:**
- Профиль/кэш — событие при изменении (или просто TTL, устаревание раз в 15 минут).
- Поисковый индекс — событие "курс опубликован/изменён" → переиндексация.
- Аналитика и рекомендации — периодические батч-задачи (ETL), не реальное время, задержка допустима.

## Список спорных решений

**1. Сессии/токены: только Redis vs Redis + PostgreSQL как backup**
- Аргументы за Redis-only: максимальная скорость, TTL из коробки, токены не критичны для долгосрочного хранения.
- Аргументы за дублирование в PostgreSQL: при падении Redis все пользователи разлогинятся одновременно.
- **Решение:** Redis-only — потеря сессий при сбое не критична для образовательной платформы (не деньги), пользователь просто перелогинится.

**2. Курсы и уроки: чистый PostgreSQL vs PostgreSQL + MongoDB**
- Аргументы за чистый PostgreSQL: проще поддерживать одну БД, меньше точек отказа.
- Аргументы за связку с MongoDB: у разных курсов разный набор полей материалов (видео, текст, интерактив) — жёсткая схема потребует много NULL-полей или EAV-антипаттерна.
- **Решение:** структура курса (курс→модуль→урок, связи) — в PostgreSQL, а содержимое/материалы урока (гибкие поля) — в MongoDB.

**3. Рекомендации: Graph (Neo4j) vs простые SQL-запросы в PostgreSQL**
- Аргументы за Neo4j: нативные запросы путей и связей, легко расширять («друзья друзей», «похожие по нескольким признакам»).
- Аргументы за PostgreSQL: команда не увеличивает число технологий, для MVP достаточно простых JOIN.
- **Решение (для этой практики):** на старте — PostgreSQL, миграция на Neo4j при усложнении логики рекомендаций.

## Проверка по контрольным вопросам

1. **Redis, но нужны транзакции?** — Нет. Сессии не требуют ACID.
2. **PostgreSQL, но растёт без лимита?** — Логи туда не помещены (они в ClickHouse) — ок.
3. **Аналитический запрос в OLTP?** — Нет, аналитика вынесена в ClickHouse отдельно от PostgreSQL.
4. **Сущность в нескольких хранилищах без описания синхронизации?** — Курсы (PostgreSQL+MongoDB) и Пользователи (PostgreSQL+Redis) — синхронизация описана в Этапе 4.
